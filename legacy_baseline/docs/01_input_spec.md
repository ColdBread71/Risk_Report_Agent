# 输入规范

## 1. 目的

本文档定义第一阶段抽取模块的输入边界与预处理行为。

目标是把混合的客户材料整理成稳定的证据单元，供 Context 抽取使用，而不是强行要求固定文件格式。

## 2. 输入原则

- 接受异构的产品材料。
- 优先使用技术信息更明确的资料，而不是营销内容更多的资料。
- 输入资料应视为证据来源，而不是天然结构化数据。
- 先读材料，再决定能抽出哪些事实。
- 如果资料噪声较大或内容较少，结果可以稀疏，但必须真实。
- 不要把文件类型硬编码成字段映射。

## 3. 推荐输入材料

第一版推荐优先处理以下材料：

- 产品介绍 / 产品宣传册
- 用户手册
- 技术手册 / 技术说明
- 架构图
- 部署 / 集成说明
- 接口或通信说明
- 长篇白皮书

## 4. 输入边界

第一版应保持在可控的输入边界内：

- 不假设客户会提供完全统一、结构化的文件集合
- 不假设每种文件类型都一定包含有用的技术事实
- 不要求在抽取前就拿到一套完美的资料包
- 允许用户提交现实可获得的材料组合
- 如果资料太薄，就返回稀疏结果，不要猜

## 5. 预处理规则

### 5.1 短文档

- 页数较少的文档可以直接作为一个 chunk。
- 如果内容本身已经很紧凑，不要强行切碎。
- 即使整篇不切块，也要保留页码和源文件元数据。

### 5.2 长文档

- 当文档较长时，可按章节、标题、页码或主题连续性切块。
- 每个 chunk 应便于证据回溯，但不要切得过碎以致上下文丢失。
- 保留 chunk 的原始顺序。
- 优先按照文档自身结构切分。

### 5.3 噪声文档

- 装饰性的宣传页、重复图片、无关营销内容，如果不包含技术事实，可以忽略。
- 混合型文档是可以接受的；抽取时保留技术部分，丢弃其他部分。
- 不要在抽取前把噪声文档强行整理成固定结构。
- 如果某页同时有噪声和技术细节，保留技术细节并记录其位置。

### 5.4 证据单元

- 每个处理后的 chunk 都应保留源文件元数据。
- chunk 应可追溯到文件名、页码 / 幻灯片页码、以及可用的局部位置。
- 预处理结果必须能作为后续抽取的证据来源。
- 短文档可以对应一个证据单元；长文档可以对应多个证据单元。

### 5.5 图片密集文档

- 架构图、表格、截图、扫描页都可以接受。
- 仅从图片中抽取可确认的技术信息。
- 如果 OCR 或图像理解不可靠，保留来源引用，把事实留待确认。
- 不要编造图片内容。

### 5.6 URL 或网页内容

- 如果提供 URL，只把它作为补充证据。
- 优先使用可见正文或技术章节，避免导航栏、营销横幅和无关页面。
- 如果网页内容无法可靠获取，不要把它当作强证据。

## 6. 预处理输出要求

预处理阶段应输出一个标准化的证据包，至少包含：

- 源文件名
- 源类型
- 页码 / 幻灯片页码 / 章节引用
- chunk 文本或抽取文本
- 顺序信息
- 可选的局部位置
- 可选的预处理备注

预处理阶段不决定最终 Context 字段。
它只负责把证据单元准备好。

## 7. 输入处理规则

- 系统应对推荐边界内的任意材料进行处理。
- 每份文档都应视作潜在的证据来源。
- 抽取器应对文档内容敏感，而不是对文件类型死板。
- 没有技术价值的装饰性内容可以忽略。
- 遇到不确定内容时，应保留来源并标记为待确认，而不是静默丢弃。

## 8. 本阶段输出

本阶段不产生最终产品画像。
它只定义抽取器应如何接收和预处理源材料。
