# emu-node012-v6 后续分阶段优化计划

日期：2026-09-14。基线：`output/emu-node012-v6/`。当前任务：基于 v6 评审逐节点优化，不预设新版本号。

本轮不一口气改完 Node0–2。按“运行机制 → Node0 → Node1 → Node2 → 独立整轮对比”推进。每个 Node 都先说明问题和改法，再修改代码、做离线检查、按明确目标运行、检查该节点结果；不为了业务内容完整或措辞完美自动循环生成。

Node1 使用优化后检查过的 Node0 实际结果及本节点所需资料，Node2 使用优化后的 Node1 结果及本节点所需资料。Node2 的累计输出可用于完整对比，不需要再从头重跑。当前仍在基于 v6 优化；未来是否整理为新版本、采用什么名称，待实际需要时确定。

Node0–2 定位为“证据提取和资产盘点草稿链”，目标优先级依次为：尽量完整保留客户材料中的对象与事实；不把未知写成肯定事实；缺失内容使用 null、空列表、条件项或待确认问题；局部质量问题只降级对应内容并继续生成；到 Node2 形成全量候选资产，再由人工筛选和确认。Node0 法律范围未正式冻结、Node1 某些上下文缺失，不阻止 Node1/2 草稿继续。只有进入后续 TARA 分析前，才要求人工批准资产及满足相应分析输入。

运行失败只用于技术完整性问题，例如 JSON 无法形成 Schema 所需结构、输入文件不可读、证据包身份/哈希异常。业务资料缺失、可选配置未知、法律结论未冻结、局部边界分类或措辞问题不得让整个节点失败；系统应保留信息、采用保守表达，并把自动降级记录在审阅提示中。

## 1. 为什么改成分阶段

当前 v6 的问题位于不同层级：Node0 主要是范围和待确认项表达；Node1 是检索事实被截断、类别混淆和综合遗漏；Node2 是资产覆盖、粒度、保护目标和证据错位。如果同时修改并整跑，结果改善或退化时很难知道是哪一层造成的，也无法判断下游遗漏究竟来自上游还是自身。

分阶段后，每一步只回答三个问题：本节点输入是否正确、本节点是否保住已有事实、本节点输出是否足以交给下游。这样既便于理解，也避免模型围绕一个节点自动反复生成。

## 2. 可复用的单节点保存机制：先用于 v6

用户日常只需要看一个平铺目录：

```text
output/emu-node012-v6/
  node0.json
  node0.xlsx
  node1.json
  node1.xlsx
  node2.json
  node2.xlsx
  report.json
  report.xlsx
  run_manifest.json
  stage_manifest.json
```

- `node0.*`：Node0 范围结果。
- `node1.*`：累计包含 Node0 + Node1，供检查产品理解。
- `node2.*`：优化后的累计 Node0–2 结果，完成后用于再次对比。
- 现有 `report.*`、`run_manifest.json`：保留 v6 原整轮基线，不覆盖，保证原 `review.md` 引用仍然成立。
- `stage_manifest.json`：单独记录优化阶段的生成时间、代码/规则版本、输出文件和上游文件哈希。目录归属 v6 不代表优化结果由原 v6 代码生成。

这是适用于任意版本目录的通用机制，不在代码中写死 v6。当前先向 v6 目录追加阶段产物；若同一节点再次运行，首次保留 `node0`，后续按 `node0_1`、`node0_2` 递增（Node1/2 同理）。`stage_manifest.json` 保留全部尝试，并把最新成功结果标为 `draft_eligible` 下游输入；失败尝试不会替换上一次成功结果。现有整轮结果中导出的节点视图只能标为“基线拆分”，不能冒充优化后真实运行结果。

字段缓存继续放在 `project_artifacts/`，不进入日常 output。版本目录中不再生成多层 `progress/`、重复 report 或临时自评文件。

## 3. 阶段 A：先改运行与保存机制，不调用模型

### 原因

当前 `main.py` 要求每个 `--run-id` 使用全新目录；单节点还从全局 `checked_upstreams.json` 找上游。这不能稳定实现“同一个 版本目录逐节点追加”，也可能让 Node1 误用其他版本的 Node0。

### 解决方案

只做小范围改造，不重构工作流：

1. 同一 `--run-id emu-node012-v6` 允许依次写入 Node0、Node1、Node2，但禁止覆盖已经存在的同名阶段产物。
2. Node1 固定读取同目录 `node0.json`；Node2 固定读取同目录 `node1.json`。读取前检查 run-id、节点状态、证据包身份和文件哈希。
3. 每个阶段使用独立缓存位置，修改 Node1/2 后不会要求重新生成 Node0。
4. manifest 分阶段记录代码和 Prompt 指纹，避免同一版本目录中不同阶段的代码状态被隐藏。
5. 保留现有整轮入口用于以后做复现测试，但这次开发不使用它。

### 离线验收

- 临时目录能够按 Node0 → Node1 → Node2 写入三个文件名。
- Node1 缺少 `node0.json` 时明确停止；Node2 缺少 `node1.json` 时明确停止。
- 上游版本、证据包或哈希不一致时明确停止。
- 已存在阶段文件不会被静默覆盖。
- 不调用真实模型，现有离线测试通过。

## 4. 阶段 B：只优化并运行 Node0

### 原因

v6 已较好识别 EMU300A + Logger5000 的基本范围，但把“节点已生成”和“法律/交付范围已冻结”混在一起。客户 PDF 无法证明 CRA 分类、适用附件、叠加法规、RDPS 必要性和实际 BOM；这些空值如果只显示为空白，用户很难判断是遗漏、失败还是确实待确认。

### 解决方案

1. 强化 Node0 的事实边界：产品 PDF 只用于产品身份、能力、组件和条件配置；不得据此编造法律分类。
2. `classification`、`applicable_annex`、`overlapping_regulations`、RDPS 等缺证据时保持空值/待确认，并在 Excel 明确显示“待法规/业务确认”。
3. assumptions/questions 至少覆盖产品版本与 BOM、交换机/选配件、云服务边界、CRA 分类与附件依据；合并重复问题，保持给业务同事看的问题数量可控。
4. 明确 Logger5000 是本轮标准内置子系统；MOXA、MPLC、PID&ISO、IO 模组、录波小板等按材料写成条件范围，不能冒充实际交付。
5. 不建设法规 RAG，不增加 Node0 模型自评分，也不让模型为了“自认为更好”自动重跑。

### 真实运行与产物

首次运行生成 `node0.json/xlsx`；有明确修复目标的再次运行生成递增尝试文件。本轮定向修复后的第二次运行将生成 `node0_1.json/xlsx`，并复用仍符合版本、模型、索引、证据包和 Schema 指纹的既有字段事实。

### 本节点检查

- 产品主体、Logger5000 和条件组件没有混淆。
- 已知事实与待确认法律/BOM问题明显分开。
- 空法律结论在 Excel 中可读，不表现为程序漏填。
- 没有新增无证据的法律结论。
- 输出可作为资产盘点草稿的范围输入。

检查结论写入本目录的 `optimization_log.md`。若只是仍有业务待确认项，记录后继续；若出现会污染下游的范围错误，先展示“错误原因 + 单一修复方案”，不自动循环运行。

## 5. 阶段 C：基于优化后的 Node0，只优化并运行 Node1

### 原因

v6 的 Node1 有三类明确问题：高密度字段被 12 条事实和 24 个检索块截断；通用字段 Prompt 不能区分组件、功能和数据；综合步骤又丢掉已经提取出的安全功能与通信事实。NTS 行还因 PDF 表格跨块而漏掉 4460 端口。

### 解决方案

1. 只为 Node1 高密度字段提高容量：communications、functions、security_functions、components 最多约 24 条事实，检索约 36–40 个 block，仍受现有 12,000 token 上限约束；普通字段保持原限制。
2. 给字段增加简短、具体的提取要求：
   - communications 按协议、端口、方向、默认状态逐条保留；
   - security_functions 按安全功能表逐项保留，并区分存在、默认启用、可选和建议；
   - components 只收硬件、固件、软件、服务或外部组件，不把升级操作和业务动作当组件；
   - functions 按独立业务/安全作用列出，不用摘要代替对象。
3. communications 的相邻块窗口扩大到 3，先修复 NTS 表格跨块问题；不重做 PDF 解析器或索引。
4. 加强 Node1 综合：字段事实中已经明确的端口、安全功能、组件必须进入结构化结果；若确实不纳入，则在 completeness notes 说明原因。
5. Logger5000 建模为采集器/嵌入式子系统，其固件、系统镜像和软件另行表达；MOXA 作为条件组件保留已知事实及“是否交付待确认”。

### 真实运行与产物

Node1 读取同目录 `node0.json`，只运行一次，生成累计的 `node1.json` 和 `node1.xlsx`。它不得重新生成或改变 Node0。

### 本节点检查

- v6 已知遗漏的 HTTP/8080、SSH/SFTP 22、MMS/102、Modbus TCP/802、UDP 9998–9999、RS232 Debug、NTP/123、NTS/4460、Syslog/514 均有记录或明确的不纳入理由。
- NTS 不再写成“端口未知”。
- 安全登录、用户密码管理、协议配置、证书管理、安全启动、安全存储/通信/对时、恢复、日志回溯和安全更新进入详细功能，而非只在摘要出现。
- Logger5000 类型正确，条件交换机没有被写成确定交付。
- 抽查字段事实到最终 Node1 的保留关系，确认综合没有再次丢事实。

结果和 v6 的变化写入 `optimization_log.md`。本阶段不运行 Node2，也不启动完整独立评审。

## 6. 阶段 D：基于优化后的 Node1，只优化并运行 Node2

### 原因

v6 的 Node2 只有 9 个资产。字段事实中已经出现重置校验码、SN、返回密钥、NTS 证书和 GOOSE 密钥，但综合后仍消失；`data_assets` 又把功能当数据，导致凭据、配置、固件、日志、网络、核心功能和外部受影响对象成片遗漏。若干保护目标还写成了具体控制或无证据的已有能力。

Node1 已在同一 v6 目录内优化到 `node1_4.json/xlsx`。它包含 36 项功能、9 项组件和 17 条通信流，能够作为 Node2 草稿输入，但其中某些“交换数据”和通用组件用途仍带有合理推断。Node2 必须把 Node1 当作候选结构，不得把上游摘要中的推断自动升级为已确认资产事实。

当前代码还有五个直接原因：

1. Node2 七个检索字段都使用默认的 24 个块、12 条事实和通用提取说明；高密度字段很容易在前 12 条停止，`data_assets` 还会优先复述功能而不是列数据对象。
2. 最终综合把 Scope、完整 ProductContext 和七类事实一次性输入，按 `node1_4` 估算约 18 万字符。单次请求容易耗时过长、漏掉中段事实或把不同类别粗略合并。
3. `_validate_asset_field_coverage` 只检查结果中是否出现“数据、密码、网络、功能”等关键词，不能证明具体事实得到处理，却可能因缺少一个词而触发整段重试。
4. `Asset` 没有简明的确认状态，导致选配组件、外部受影响对象和真正已确认的产品资产只能写进描述，模型容易直接丢弃或写成已经交付。
5. 任一字段或最终综合失败时，整个 Node2 不生成资产；这不符合“局部缺失保留说明、其余内容继续输出”的工作原则。

### 解决方案

本阶段分三步修改代码，全部完成离线检查后只运行一次正式 Node2，不在每一步调用真实模型。

#### D1：修正七类字段事实和资产契约

1. 为七类字段分别写简短、明确的提取说明，只为高密度字段增加事实容量和候选块：
   - `data_assets`：只提取被存储、处理、传输、导出或删除的数据；区分运行/遥测数据、控制指令与设定值、配置、日志和网络拓扑信息。
   - `credentials_and_keys`：区分本地/Web/OS/LDAP 凭据、设备 SN、重置校验码与返回密钥、证书与私钥、GOOSE 密钥、升级验签公钥、导出/备份密码和远程维护访问信息。
   - `software_and_configuration`：区分 Logger5000 固件/OS/启动镜像、升级包、设备/网络/协议/调度/安全配置和备份文件。
   - `hardware_and_network`：提取 EMU300A、Logger5000、明确接口、南北向网络和相邻设备；MOXA、MPLC、PID&ISO、IO、光纤组件保留选配或 BOM 待确认限定。
   - `external_services`：阳光云、三方云、远程维护、时间服务和 Syslog 等分别处理，不自行判定 RDPS。
   - `function_assets`：按业务功能和安全功能簇提取，不能只复述操作步骤。
   - `user_property_environment`：提取人员、相邻生产设备/系统、生产连续性、人身和财产影响；没有环境或公共利益事实时不虚构。
2. 为容易漏掉的重置材料、证书/密钥、日志与备份、升级验签、调试接口等增加少量定向检索锚点，避免单纯扩大所有字段。
3. 给资产增加一个供工程师查看和筛选的“状态”字段：`confirmed`、`conditional`、`external_affected`、`needs_confirmation`。默认关闭的功能仍可为 confirmed；只有是否交付/是否存在未定时才用 conditional 或 needs_confirmation。
4. 资产类型限定为受信指导文件覆盖的少量类别，避免同义词漂移；不增加风险、威胁或评级字段。

#### D2：拆分综合并允许局部降级

1. 把一次超长综合拆成三个有独立缓存的段：
   - 数据、凭据、软件与配置；
   - 硬件、接口/网络与外部服务；
   - 产品功能、用户、财产和其他受影响对象。
2. 每段只接收相关字段事实和精简的 Node1 结构。Node1 的功能/组件/通信只提供候选清单；资产存在和位置以直接字段事实为准。
3. 三段结果由代码确定性合并、重新编号，并只对完全相同的对象去重；不使用模糊关键词把不同用途的资产强行合并，也不再调用一次全局 LLM 重写全部资产。
4. 某一段技术失败时记录该段缺口，仍导出其他成功段并把总体结论设为 PARTIAL；只有所有段都没有形成资产时才判定 Node2 失败。
5. 删除 `_validate_asset_field_coverage` 关键词业务校验。只保留 JSON Schema、ID 唯一、枚举值、证据 block 合法及引用归属等技术校验；技术格式重试保持有界，不因材料缺失或类别不完整而重试。

#### D3：纠正资产粒度、保护目标、证据和 Excel

1. 同一生命周期、用途和保护目标相同的对象合理合并；不同用途或不同保密要求的对象分开。不会为 17 条通信流各建一个资产，也不会用“EMU300A 整机”吞掉全部数据、凭据、固件和功能。
2. 网络、外部服务、相邻生产设备/流程、人员和财产可以作为外部受影响资产；“不是产品组件”不是排除理由。环境、公共利益等没有事实支持时写入待确认说明。
3. 条件组件只生成 conditional 资产或待确认项，不冒充实际 BOM；开关电源、防雷和断路器等没有独立数字攻击面的普通硬件可归入整机物理平台，不要求逐个生成网络安全资产。
4. 保护目标只写希望保持的结果，例如“控制指令来源可验证且内容完整”“配置仅由获授权主体修改”。不得把 TLS、防爆破、安全存储、不可删除、完整擦除等具体控制写成已经实现的目标效果。
5. 证书本身不默认要求保密；私钥、密码、重置密钥等秘密材料才以保密性为主要目标。关键控制/调度功能及其数据按事实考虑完整性、真实性和可用性。
6. 证据支持资产存在及其价值；位置没有直接依据时保持 null。`eMMC`、完整清除范围、具体日志事件等不能按常识补写。
7. Excel 在现有资产—目标表中增加“资产状态”列，继续自动换行、合理列宽和冻结表头；不再增加额外业务页签。

#### D4：补充功能—资产关系并纠正过度合并

首次Node2结果显示：Node1共有36项产品功能，其中20项为安全功能；Node2虽形成31项资产，但只有5项功能资产，且Schema没有保存功能与资产的关系。资产总数不要求大于功能数，但每项Node1功能都必须能追踪到至少一个资产，重要功能本身也应被合理成组为功能资产。

1. `Asset`增加`related_function_ids`，复用Node1的`FUNC-xxx`建立多对多关系；一个功能可涉及数据、凭据、软件、硬件、接口和功能等多个资产，一个资产也可服务多个功能。
2. `functions_impacts`分段必须让每个Node1功能至少出现在一个功能资产的关系中。登录与访问、南向采集、控制调度、北向转发、配置管理、时间同步、安全通信、证书密钥、可信启动/安全存储、日志审计、更新、恢复等可按共同价值成组，不要求36项一一对应，也不得压缩到少数业务功能后遗漏安全功能。
3. 功能资产可直接复用Node1已经验证的功能证据块；其他类别仍须由Node2字段事实证明存在。这样不重复提取相同功能，也不把Node1候选名称误当成数据或组件证据。
4. 合并后由代码删除未知/重复功能ID，并分别报告“没有任何资产关系”和“没有功能资产覆盖”的Node1功能。缺口只使总体结论为PARTIAL并写入说明，不报错、不触发模型重试。
5. 现有资产表增加“关联功能编号”和“关联功能名称”，保留筛选、状态色、自动换行和冻结表头，不增加新页签。
6. 同时收紧首次结果暴露的错误：不把GOOSE密钥推断为私钥/签名密钥，不假定重置密钥单次或限时，不扩大日志与备份内容，不把无数字逻辑的光纤终端盒单列网络安全资产，也不把阳光云推断为未证明的时间或远程维护服务。

#### D5：对 `node2_1` 做一次小范围纠错

`node2_1` 已把36项Node1功能全部带入资产关系，但三个分段分别猜测关系，导致若干编号形式正确、业务含义错误。例如Syslog和NTP/NTS被关联到登录或密码功能，阳光云被关联到与云上传无关的功能；日志、更新和恢复仍有过度合并。该问题比继续补充材料缺口更容易误导工程师，因此在进入独立对比前只做一次定向修复。

1. 三个资产分段继续负责“有哪些资产”，合并后增加一次小型、独立的资产—功能映射；它只能复用现有资产ID和Node1功能ID，不能增删或改写资产。
2. 映射不以覆盖率强迫模型填号。专门步骤漏回某个资产、返回未知ID或技术失败时，代码保留该资产的分段临时关系、清理无效ID、将总体结论降为PARTIAL并继续导出，不触发业务重试。
3. Prompt明确区分时间同步、日志审计、软件更新、复位恢复、证书密钥和安全存储等功能簇；时间服务、Syslog、云平台及网络接口只关联材料支持的实际用途。
4. 对完全没有直接证据的候选，代码将描述、价值和位置中的推测内容改为中性待确认文字；证书资产不得用未单列的私钥泄漏来描述自身价值。
5. 数据/凭据/软件段补查操作系统凭据、私钥与升级包；系统/服务段补查EMU平台、数字选配组件及有事实的相邻网络设备，并继续排除无数字逻辑的光纤终端盒。`value`只写直接支持的用途或一般后果，不提前写具体攻击和灾害链。

本步不增加自评、多代理复核或自动业务循环。首次执行时规则改变使三个资产分段缓存失效，新映射需要一次调用，因此通常为4次文本LLM调用；七类字段事实仍按内容指纹复用。`node2_2`在三个分段成功后因空保护目标触发合并错误，作为失败记录保留；修复后再次运行会复用三个成功分段，只执行统一映射，目标产物改为同目录的`node2_3.json/xlsx`。

#### D6：换项目之前的通用性与可读性收口

`node2_3`的资产数量已进入可人工修订的合理区间，不再围绕当前项目继续补齐未知信息。换用另一项目材料前，只处理会迁移错误或明显误导工程师的问题：

1. 生产Prompt、检索查询、定向锚点和确定性纠错不得写入本参考项目的名称、型号、专有云平台、专用接口或端口；人工Excel不得进入生产输入。以通用的整机、嵌入式子系统、数字模块、接口边界、外部平台、时间/日志/目录服务等概念表达规则。
2. 资产状态只根据该资产自身的范围事实判断；不得因为描述里提到一个选配子组件，就把整机或上层平台一起改成conditional。
3. 无数字逻辑的被动支撑件并入平台或网络路径；证据证明其有固件、配置、管理、处理或控制能力时仍保留。证据未支持的具体攻击或灾害链从资产价值中移除。
4. 非function资产若一次关联大量功能，说明统一映射未能区分主要直接关系。此时清空辅助关系并标为PARTIAL，交给工程师确认；不删除资产、目标或Node1功能。
5. Excel仍按一个cybersecurity objective一行输出；同一资产的共同字段跨目标行纵向合并，目标列保持逐行独立。
6. 增加自动通用性测试，阻止参考项目专有词和人工基线路径重新进入生产规则。先用另一项目实际运行验证迁移效果，再决定是否重跑当前项目或进入完整对比。

#### D7：最终 Prompt 审阅与纠错一致性检查

1. 把字段抽取、Node0、Node1、Node2及后续Node3的生产Prompt从节点代码迁入`prompts/`，每段写明调用节点、代码、输入和用途；注释不得进入模型上下文。
2. 专有词自动扫描覆盖所有生产规则和Prompt，并使用单词边界检查英文缩写；参考项目的行业对象、协议、平台、组件、接口、端口和当前结果数量都不得成为通用规则。
3. Prompt与确定性纠错必须一致。功能关系过宽使用相对覆盖判据，不使用固定“超过8项”规则；位置、资产状态、被动部件和攻击链纠错均使用通用语义，不写具体项目技术名。
4. 用现有`node2_3`只读回放纠错影响，不调用模型、不改写产物；随后跑全套测试。通过后本轮Node2代码优化结束，下一次真实运行只用于观察结果，不在运行中继续改代码。

### 本轮预期处理范围

本轮不预先规定资产总数。以下类别必须逐类得到“已列资产、合理合并、条件资产、范围不适用或材料不足待确认”之一，不能无说明消失：

- 运行/遥测/业务数据，控制指令与功率设定值；
- 用户与系统凭据、设备标识和密码重置材料；
- 证书/私钥、GOOSE 密钥、升级验签材料和临时导出密码；
- 固件/OS/升级包、配置/备份和日志数据；
- EMU300A、Logger5000、调试/管理/现场接口及南北向网络；
- 数据采集转发、调度/功率控制、设备配置管理等核心业务功能；
- 登录与权限、证书密钥、安全通信、安全启动/升级、日志审计、时间同步、恢复出厂和远程维护等安全相关功能；
- 阳光云、三方云、时间/Syslog 服务及相邻站控、SCADA、逆变器、电表等系统或设备；
- 运维人员、生产运行/连续性、人身和财产影响，以及有证据时的环境或公共利益对象。

## 8. 运行与重跑规则

1. 每阶段正常情况下只有一次真实模型运行；代码修改前先做不调用模型的离线测试。
2. API/网络中断、无效 JSON 等技术失败不算有效结果；先修技术问题，再由用户手动重跑该阶段。
3. 业务效果不理想时不自动重跑。先在 `optimization_log.md` 写清“看到的问题、根因证据、拟修改内容和会影响的输出”，再决定进入下一版本还是做一次有明确目标的修复。
4. 运行过程中不改代码；阶段产物生成后只读检查，不人工润色 JSON/Excel 来伪装模型效果。
5. Node0 的法律/BOM待确认不阻止 Node1/2 生成资产草稿，但最终报告不得据此进入 Node3。

## 9. 本轮明确不做

- 不运行 Node3，不开发 Node4–8。
- 不把人工 Excel 答案写入生产 Prompt。
- 不重做 PDF 解析器、证据包或 FAISS 索引。
- 不增加模型自评分、多代理评审或自动业务循环。
- 不进行新的整体架构重构。

## 10. 完成标准

本轮分步优化完成是指：三个节点按顺序各生成一次可追溯产物；每一步在 `optimization_log.md` 中都有原因、改法、结果和剩余问题；最终独立评审能够逐项判断 v6 的 REV-001～REV-005 是否改善。业务同事仍负责确认法规分类、BOM和真实配置，本开发结果的目标是成为清晰、可追溯、没有已知成片遗漏的评审草稿。
