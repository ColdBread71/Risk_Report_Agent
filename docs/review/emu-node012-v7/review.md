# emu-node012-v7：Node0–2 独立业务结果评审

## 1. 评审对象与口径

本报告将 `emu-node012-v7` 作为首轮、无既有结论的独立结果进行评审，不沿用其他版本的评审意见。

实际结果文件：

- `output/emu-node012-v7/report.json`
- `output/emu-node012-v7/report.xlsx`
- `output/emu-node012-v7/run_manifest.json`

事实材料：

- `legacy_baseline/Project/阳光EMU项目/EMU300A-UCN-Ver11-202603.pdf`
- `legacy_baseline/Project/阳光EMU项目/EMU300A网络安全操作手册-UCN-Ver11-202607.pdf`
- `legacy_baseline/Project/阳光EMU项目/logger5000用户手册=GUID-00B9E4B6-10C1-4C13-B46E-1BF52C86BC71=1=PDF (产品信息设计部_基础版)=zh-CN (9).pdf`
- `legacy_baseline/Project/阳光EMU项目/产品安全风险与安全需求分析-20260727.xlsx`（仅作人工资产覆盖与工程表达对照，不作为 PDF 事实的替代来源）

`run_manifest.json` 与 JSON、Excel 的运行标识和生成状态能够对应，Excel 也包含 Node0–2 结果。但 JSON 同时记录了分段技术失败，因此不能仅依据顶层 `asset_identification_completed` 判断本轮已完整完成。

## 2. 总体结论

**结论：本轮不完整。**

当前产物不宜交同事做正式业务评审，也不宜直接作为后续 TARA 的资产输入。核心原因不是资产数量少，而是 Node2 明确记录了 `data_assets`、`hardware_and_network`、`functions_impacts`、`user_property_environment` 四个分段未完成，导致整个资产类别被系统性清空；与此同时，顶层状态仍显示资产识别完成并等待审批，容易把技术失败伪装成业务结论。

正面变化也很明确：结果已经能区分资产状态、保护目标依据和确认状态，并使用带类型的功能关系；`review_summary` 的 10 项资产、16 项保护目标、10 项 supported、6 项 needs_confirmation 与实际输出一致。多数 surviving assets 的存在性证据可追溯，保护目标也比常见的“全属性默认保护”更克制。这些结构值得保留，但无法抵消本次运行不完整。

## 3. 当前最重要的五个问题

### 3.1 Node2 四个分段技术失败，资产结果不是完整集合

**证据位置：** `report.json > errors`；`asset_identification.notes`。

顶层错误明确显示 `functions_impacts` 因模型给出非法 `asset_type = system`，两次提取均失败。notes 还明确记录 `data_assets`、`hardware_and_network`、`user_property_environment` 为 `technical_failure`。最终 10 项资产只有 credential、software、service 三类，没有 data、hardware、network、function、user、property 等类别。

**业务影响：** 日志、配置、证书/私钥、控制指令、通信数据、备份、接口、EMU/Logger 载体、关键功能、用户与受影响对象等已被材料直接支持的候选资产无法进入 Node2，后续威胁场景和风险分析会在输入层发生结构性漏项。

**期望纠正：** 修复枚举校验/归一化及分段重试或降级合并机制；任一必需分段失败时，整体状态必须显式为 incomplete/failed，不能发布为完成待审批。完成后重新运行 Node2，并验证各资产族均已执行，而不是人工补写本次结果。

### 3.2 完成状态与真实运行质量冲突

**证据位置：** `report.json > workflow_status/current_step/awaiting_asset_approval` 与 `errors`、`asset_identification.notes`。

结果同时声称 `asset_identification_completed`、等待资产审批，又承认四个资产分段失败。摘要只统计成功留下的内容，没有暴露“预期分段数、成功数、失败数”。

**业务影响：** 审批人很可能把“没有数据资产/硬件资产/功能资产”理解为模型判断，而不是管线故障；这比普通空字段更危险。

**期望纠正：** 将技术完整性设为业务完成状态的前置门槛；在 JSON、Excel 摘要和 manifest 中同步输出分段健康状态，并在失败时阻断 `awaiting_asset_approval=true`。

### 3.3 Node0 范围状态存在自相矛盾和标准件误降级

**证据位置：** `scope.scope_description`、`in_scope_components`、`conditional_scope_components`、`out_of_scope_components`；产品手册第 16、54–55 页。

- `scope_description` 先把光纤交换机、光纤终端盒列入评估范围，后又把同类对象描述为“不包含”；光纤交换机同时出现在 conditional 和 out-of-scope。
- MPLC 同时作为范围描述中的组成、in-scope 能力和 conditional 组件出现，缺少“产品能力存在、实物数量依 BOM”的清晰拆分。
- RS485 在产品手册和网络安全手册中均有直接描述，却因所谓“范围分类冲突”被降为 conditional。
- 开关电源、防雷模块、微型断路器在产品手册第 55 页明确属于“内含”，Node1 仍将其 scope status 设为 unknown。
- “以太网南向通信接口”缺少明确材料支持；材料主要将以太网用于北向/维护连接。

**业务影响：** 可选实物、标准内置部件和逻辑能力混在同一层级，直接影响硬件、接口及后续攻击面资产的纳入标准。

**期望纠正：** 对“能力存在”“标准交付”“可选 BOM”“客户侧外部设施”分别建模；同一对象只允许一个最终范围状态，并保留冲突来源供人工确认。

### 3.4 Node1 通信矩阵保守过度且仍不完整

**证据位置：** `product_context.communication_matrix`；网络安全操作手册第 12、14–15、26–28 页；Logger5000 用户手册第 71、76–82 页。

17 条通信记录保留了协议和端口，但全部 `direction` 为空、业务数据方向均为 unknown，明确写在源材料中的用户名/密码认证也多被丢失，`data_exchanged` 全为空。矩阵未覆盖 Syslog、GOOSE、南向 RS485/Modbus RTU、MPLC 等材料已支持的通信事实。IEC104、Modbus 端口范围的拆分还产生了端口不完整记录。

**业务影响：** 无法可靠判断数据和指令的进出方向，也无法把日志、控制、配置、证书、远程维护等资产挂接到真实通信路径；会影响外部平台资产、接口资产和后续 STRIDE/TARA 场景边界。

**期望纠正：** 对材料明确的“源设备→目的设备”至少填写连接方向；认证、加密和默认启用状态按原文保留；业务载荷未知可以留空，但不能因此删除已知流。端口范围应保留为范围或拆成语义完整的记录。

### 3.5 surviving assets 仍含不受证据支持的信息、错误状态和错误关联

**证据位置：** `asset_identification.assets`。

- ASSET-002 把 root 凭据标为 conditional，但手册第 16 页直接列出 root 和 sg 两个操作系统用户；“需要授权生成动态密码”不等于资产是否存在不确定，而且 sg 凭据被遗漏。
- ASSET-003 将公钥具体化为 RSA/ECDSA，材料只支持 `.pem` 公钥和数字签名校验，没有给出算法。
- ASSET-004 将固件/系统镜像称为“启动链根信任锚点”，原文只说明镜像被逐级验证，未说明镜像本身就是根信任锚。
- ASSET-005 的 MOXA 交换机固件标为 confirmed，而交换机是可选配置；有操作附录只证明该型号存在适用指导，不能证明当前交付包含它。
- ASSET-006 将 IEC104、Modbus、MQTT、GOOSE 全部逐一关联到阳光云。材料支持这些协议可用于北向转发，也明确 MQTT 云端口，但没有建立每一种协议到阳光云的逐项端点对应；其价值描述中的功率调度优化、合规上报和本地控制降级也缺少直接依据。
- ASSET-008 关联到“Web 数据转发配置”时使用 `transmits`，实际该功能是配置行为，不是数据传输行为；“客户私有云、行业平台、定制分析”属于材料没有给出的扩展描述。
- ASSET-009 的资产和保护目标引用第 77 页时间源/云配置片段，但该片段没有出现 NTS；“高精度、抗中间人攻击”以及 SOE、录波、保护误动等后果也未被该证据支持。NTS 的直接证据应回到端口矩阵和证书导入说明。
- ASSET-010 实际可由网络安全操作手册端口矩阵直接支持，却被写成“间接支持”，且没有关联时间同步功能。

**业务影响：** 即使忽略技术失败，现存资产仍会把假设当事实、把配置功能当传输功能，或把可选组件当已交付组件，不能直接进入正式 TARA。

**期望纠正：** 强制描述、价值、状态、功能关系分别做证据蕴含校验；禁止从通用安全常识补充具体算法、攻击路径或灾害后果。端点—协议关系只能在材料明确对应时建立。

## 4. Node0 与 Node1 对资产识别的支撑评价

### 4.1 Node0

Node0 能识别 EMU300A、Logger5000、北向远程能力、可选模块及 CRA 分类材料不足，且没有编造 PDE/RDPS 法律结论，这是可保留的优点。主要问题是范围状态的归并逻辑不稳定：物理交付状态、逻辑能力和外部依赖混写，导致同一对象跨列表冲突。当前 Node0 可以作为人工讨论底稿，但不能作为自动资产筛选的稳定门槛。

### 4.2 Node1

41 项功能覆盖了数据采集、协议转发、控制、账号、证书、安全启动、安全存储、日志、更新、时间同步和 GOOSE 安全等主要能力，颗粒度总体有用。13 项组件也识别了标准件与可选件，但部分直接证据被错误降级为 unknown，且包含风扇、插座、光纤终端盒等通常不应自动成为独立网络安全资产的被动物理部件。它们可保留在组件清单，不应仅因“是组件”就进入 Node2。

通信矩阵是当前 Node1 对 Node2 的主要短板。它会实际造成以下影响：

- Syslog 流缺失，使日志数据、日志传输和外部日志服务的完整资产链断裂；
- GOOSE 流缺失，使 GOOSE 报文、密钥和防重放功能难以关联；
- RS485/Modbus RTU 与 MPLC 流缺失，使南向采集数据、参数、控制及可选模块边界不完整；
- 已知方向和认证信息被清空，使 Web、SSH/SFTP、北向协议和云连接难以形成可信的数据流图；
- 外部平台的协议端点对应不清，促成 Node2 对阳光云的过度关联。

## 5. Node2 专项评价

### 5.1 资产覆盖

当前 10 项资产不是“精简后的完整清单”，而是技术失败后剩余的清单。按材料和人工成品的资产主题对照如下：

- **已覆盖：** Web 用户账号凭据；升级验签公钥；安全启动相关镜像；阳光云、Syslog、三方云、NTP/NTS 等外部服务的基本存在性。
- **部分覆盖/合并过粗：** 操作系统凭据只覆盖 root，未覆盖 sg；Web 用户凭据把不同角色合并，可接受但应保留权限差异；交换机只保留固件，未覆盖其配置、账号、日志和转发功能；云服务存在性覆盖了，但协议和功能关系过宽。
- **确有遗漏：** 操作/安全/Syslog 日志，运行数据、南向采集数据、北向转发数据、调度/控制指令，IEC104 点表、GOOSE/MMS 配置、RS485/网络参数，备份与恢复包，远程访问/维护信息，升级包；登录证书、客户端/服务器/NTS 证书及私钥、GOOSE 密钥、重置校验码/密钥；EMU/Logger、RS485/以太网/MPLC 等载体与接口；关键功能资产；用户与设备/电站等受影响对象。这些主题在 PDF 中有直接或可合理归并的事实，不应以“客户材料不足”解释本次缺失。
- **范围不适用：** 光纤终端盒、线缆、风扇、插座等被动部件通常不应单独列为网络安全资产，除非后续材料证明其自身承载可攻击数字功能或独立安全价值。
- **材料不足待确认：** 实际 BOM 中是否安装 MOXA 交换机、MPLC/PID/IO 等可选模块；外部云、站控、SCADA、Insight 的实际部署和责任边界；各通信能力在交付配置中的启用状态。

从“能否明显减少工程师整理工作”看，当前 Node2 尚不能，因为工程师必须先识别哪些类别是技术失败，再重新补建大部分资产链。

### 5.2 错误信息

错误信息的优先级高于空白字段。当前主要错误包括：无证据的 RSA/ECDSA 算法、root 条件状态、可选交换机 confirmed、固件镜像“根信任锚”、云端功能与后果扩写、NTS/NTP 证据错配。Web 凭据、root、Syslog、三方云和 NTS 的价值描述中还出现了具体后门、拒绝服务、监管失败、下游污染、保护误动等材料未直接支持的攻击或灾害链，应删除或降为待确认的分析假设。

### 5.3 证据质量

资产存在性层面，Web 用户、公钥、安全启动、Syslog、三方云等证据位置总体可核查。问题集中在三类：

1. 证据仅支持“存在”，却被用于支持具体算法、能力或后果；
2. NTS/NTP 使用了不包含该对象的时间源/云配置片段，证据与结论不对应；
3. 范围状态没有遵循产品手册对“内含/可选”的直接描述。

因此“有 evidence”不能等同于“evidence 支持完整描述”。

### 5.4 功能关联

带类型的功能关系比无类型 ID 列表更适合后续处理，但当前只有 17 条关系，notes 明确列出大量 Node1 功能未关联资产，并且 41 项功能没有任何 function 类型资产覆盖。登录、公钥、安全启动、Syslog 和 NTS 的基本关系方向大致合理；阳光云的协议关系过宽，三方云的 `transmits` 关系类型错误，NTP 没有关联时间同步功能。由于 `functions_impacts` 分段失败，不能据此评价为“功能资产不重要”，只能判定为未完成。

### 5.5 网络安全目标

将目标标为 `supported` 或 `needs_confirmation`，并记录 `basis`，是本轮最明显的结构进步。16 项目标没有机械地给每个资产套满全部属性，阳光云和 NTP 的证据不足也至少部分被暴露。

但目标质量仍有问题：NTS 的 integrity/authenticity 目标标为 supported，而所附证据不含 NTS；Syslog 的价值描述强调中断/不可用，目标却只有 confidentiality 和 integrity，没有解释 availability 的取舍；多项 supported 目标实质依赖未经证据支持的价值/后果扩写。更重要的是，缺失资产对应的目标整体没有生成，因此当前 16 项目标不能被视为完整目标集。

## 6. 上一轮问题状态

本报告按首轮独立评审执行，**上一轮报告：无**。因此没有可标记为“已解决、部分解决、未解决、不再适用或材料不足待确认”的既有问题。

## 7. 代码应修复的问题

1. 修复资产分段返回非法枚举值时的归一化、局部重试与安全降级；不得因单项非法值丢弃整个分段。
2. 把必需分段成功率纳入整体完成状态，并在 JSON、Excel、manifest 中一致呈现；技术失败时阻断业务审批状态。
3. 修复 Node0 同对象多状态合并规则，明确区分产品能力、标准件、可选 BOM 和外部依赖。
4. 修复 Node1 通信矩阵对显式源/目的、认证、加密、默认启用状态的丢失，并补齐 Syslog、GOOSE、RS485/Modbus RTU、MPLC 等材料支持的流。
5. 加强 Node2 的逐字段证据蕴含校验和端点—协议关系校验；禁止补写未见于材料的算法、攻击路径、灾害后果或已有安全能力。
6. 对可选组件的资产状态继承 Node0/Node1 的 conditional 结论；被动物理部件不得自动资产化。

## 8. 客户材料缺失、需要人工询问的问题

以下问题不能靠继续修改生成规则得到事实答案：

1. 当前评估交付的准确 BOM、硬件/软件版本，以及 MOXA 交换机、MPLC、PID&ISO、IO、Logger4000/5000 的实际配置关系是什么？
2. 阳光云、三方云、Insight、SCADA、站控、核心交换机在目标部署中的实际端点、运营责任、数据处理责任和断网降级行为是什么；哪些属于 CRA 意义下的 RDPS？
3. 各北向/南向协议实际启用哪些端口、传输哪些数据或指令、由谁发起；端口矩阵中的 TLS/无加密描述是否与真实实现一致？
4. 证书、私钥、GOOSE 密钥、重置校验信息、备份包、远程维护凭据的实际生成、存储、更新、吊销/清除和恢复流程是什么？
5. 产品的正式 CRA 分类、适用附录、重叠法规与制造商责任结论是什么？现有材料不足以自动下结论。

## 9. 建议的下一步

**建议继续修复本项目的运行完整性，不要立刻把当前 v7 用于第二个项目验证。**

这里需要的是一次有边界的阻断性修复，而不是围绕 EMU 继续扩充专用规则：先解决分段失败、完成状态、范围冲突、通信事实丢失和证据不蕴含五类通用问题；随后仅重跑 Node2（如依赖链要求则按最小必要范围重跑）并做一次快速验收。验收至少应满足：所有必需分段成功、错误列表为空、完整性状态真实、主要资产族不因技术失败缺席、无材料不支持的具体算法/攻击后果、可选组件状态正确。

达到这些门槛后，应停止针对本项目继续调参，转入第二个项目验证通用性。
