## 代码观察：等对比后再决定是否改

1. `nodes/field_extractor.py` 的通用提示词将每个字段限制为最多12条事实。对于功能、数据、凭据等类别可能过度压缩。不能仅靠提高最终输出长度弥补上游未留下的事实。
2. `nodes/asset_threat_modeler.py::_validate_asset_field_coverage` 用关键词存在与否判断类别是否出现。例如一个描述中有“日志”就可能满足data类别检查。这不是逐项完整性检查，且可能触发综合重试。本轮未改，待对比确认是否应该改为人工可见的缺口提示。
3. 当前RAG只查证据包批准范围，不是全部335页。原包记录拓扑图尚未转成结构关系，Logger4000适用性未确认。不能把检索不到直接判成产品不存在。
4. Node1的上下文与接受准则在一个try块生成，接受准则失败时已生成上下文不进入返回状态。这可能增加失败恢复成本，但本轮未改运行语义。
5. 业务指导要求把标准中有、产品材料未识别的安全功能单独列出；当前可执行路径未见独立的标准功能对照输出。这是待处理的覆盖能力，不应把标准要求当成产品已有能力生成资产。

保留现有分层有价值：main是入口，nodes负责步骤，schemas规定字段，tools处理材料，exporter负责给人看。没有证据支持再次推倒重构。
